## Assistant (2026-07-30T06:09:24.713Z)

Yes, that's a solid, idiomatic pattern. A few reasons it's good:

- **Exception filters** (`when (...)`) let you catch only the specific error you know how to explain, while any other `SqlException` (timeout, network unreachable, permission denied elsewhere, etc.) falls through to your generic `catch (Exception ex)` below and still logs the full stack trace — you don't lose diagnostic detail for cases you didn't anticipate.
- It's more precise than checking `ex.Message.Contains(...)` (fragile string matching) — `Number` is the actual SQL Server error code, stable across message wording/locale.
- It documents intent right in the code: anyone reading it immediately knows "4060 = can't open database" without digging into the body.

One caveat: it only matches *this exact* error code. If you later hit a sibling case like error `18456` (login failed for user, but not a "can't open database" issue) or `-2`/`53` (timeout/network unreachable), those won't get the friendly message — they'll fall to the generic handler with the full stack trace, which is fine but less readable. If you want, I can add a couple more known SQL error codes to the friendly-message list (18456, 53, -2 for timeout) so the common connectivity failures all get clean one-liners instead of stack traces — let me know if that's worth doing now or if you'd rather wait and add cases as you actually see them in the logs.
